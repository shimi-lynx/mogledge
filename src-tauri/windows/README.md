# Windows installer template

`installer.nsi` derives from the official [Tauri `tauri-v2.12.1` NSIS template](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). The unmodified source has SHA-256 `dabed59013b1d78b879a1a85bc7f2eed2993b33a9a90cdabe5946de3d3950597`. Tauri distributes it under MIT or Apache-2.0; this copy uses the included [MIT license](LICENSE-MIT).

Current installations use `Mogledge` for display, Uninstall/product registry keys, installer language, default directories and autostart. The executable is `mogledge.exe`; the bundle identifier is `com.shimilynx.mogledge`.

The installer reads the exact previous `My Knowledge` product keys only to detect an owned installation. Publisher, recorded executable name, exact uninstaller command and both installed files must match before overwrite upgrade is allowed. Unverifiable predecessors stop installation. An existing fixed/custom install directory is preserved, including a previous default directory whose basename is still `My Knowledge`; a different directory requires a separate uninstall first. A fresh installation uses Mogledge directories. No old profile or document-data directory is searched, copied or deleted by this compatibility path.

After copying the new executable, overwrite upgrade retargets owned shortcuts and the exact old no-argument Run command, writes the Mogledge product registration and removes the verified old installer registration. Foreign shortcuts and Run commands are preserved. A nonempty legacy Run entry containing arguments or any unsupported command stops the upgrade before copying/deleting application files or rewriting installation/startup registration. Resolve that registration explicitly before retrying; the installer neither parses nor retargets unknown arguments. A conflicting new-name Run command also stops the upgrade before file replacement. A foreign new-name shortcut can leave an owned old-name link in place, retargeted to the new executable. This collision exception avoids replacing another application's link. Existing shortcut targets named Mogledge are also retargeted when they point to the old binary. Normal uninstall-before-install can disable autostart through the old uninstaller, as in upstream; overwrite and `/UPDATE` preserve the enabled registration. The installer relaunches the new executable.

Keep the upstream template changes limited to these compatibility requirements. Reconcile this file with the official template whenever the Tauri CLI/bundler version changes. The [0.10.1 release record](../../docs/release-0.10.1.md) covers earlier candidate and bounded Native checks; those shortcut assertions did not check explicit icon references. Before a release containing this repair, verify fresh/default/custom locations, normal and `/UPDATE` flows, new-binary relaunch, version comparisons, registration cleanup, shortcut collisions and autostart enabled/disabled states. Static source checks cannot establish a working installed update.

## Shortcut icons after the executable rename

Fresh Start-menu and desktop links use the current executable as their default icon source. Reusing an existing link is different: Tauri's `SetShortcutTarget` changes its target and preserves an explicit icon location. If that location still names the removed `my-knowledge.exe`, a working link can display a generic file icon. This condition can arise during an overwrite migration or other retargeting; it is not specific to the in-app updater. The original creation history of an affected link cannot be established from its current properties alone.

After an existing link passes the ownership checks, the template repairs only an icon path exactly matching the old executable inside the verified install directory. It preserves default icons, custom icon files, arguments, descriptions and foreign links. A matching current-name link also receives the repair. Existing taskbar pins are independent copies; this template does not enumerate or rewrite them. A device-specific repair must verify their target and AppID, preserve backups outside app-link search locations, and change only the stale icon reference.

Focused verification covers 20 source-model cases in `windows-identity.test.mjs`; the unchanged template failed six cases. A Windows shortcut-only NSIS/COM fixture reproduced the stale explicit-icon reference with the released macro and verified fresh creation, repaired migration, an already-current target, default/custom icons and the foreign-link collision using the changed macro. Shell icon extraction was normal for fresh and repaired links. These are real shortcut operations without an application installation or profile access. They do not establish a full fresh-install, overwrite or in-app update run for this patch. The local rendered installer inspected during diagnosis was historical 0.8.1 output, not evidence of a newly generated 0.10.1 installer.

The hosted Native probe now seeds an explicit predecessor icon and checks default/current icon references together with the target and AppID. That full hosted installer probe remains unrun for this draft. Reuse the existing release checks at the next authorized integration; no application rebuild, installation, merge or release is part of this correction's draft verification.
