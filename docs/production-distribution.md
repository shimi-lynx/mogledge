## Build once from the final candidate source

Merge the reviewed packaging preparation before selecting the final full main SHA. Build all intended 0.8.2 candidates from that same SHA; later policy-only tooling commits have separate SHAs and do not require rebuilding these binaries. Avoid duplicate Actions runs and reuse an existing matching Windows cache with one Rust job; do not copy or clean the cache. Existing installed applications and profiles are not build fixtures.

The manual candidate workflow accepts `updater_app: true` with Windows x64, either Mac target, or all three concurrently on separate standard runners. Each OS retains one Rust job; heavy Windows validation in the same environment remains sequential. The workflow's ref-based concurrency group still prevents simultaneous runs for the same ref. Cost and legal-material confirmations remain required. Do not change the existing $0 additional budget, payment method, repository security settings or authentication. Failed operations stop for diagnosis; no blind retry or automatic re-signing is authorized.

Windows compiles the explicit updater overlay once using the native x64 MSVC cache layout. It then bundles that executable as NSIS with CLI updater signing disabled. Neither step receives production Secrets. The existing NSIS template, current-user installation location and uninstaller identity are retained. Inspection checks installer name/PE versions/unsigned status, extracts with existing 7-Zip without executing the installer, and compares the actual bundled EXE and every embedded legal/source file. The bundler's NSIS marker is included in the final payload hash; an earlier unbundled EXE hash is not substituted. The ordinary ZIP also carries the EXE and legal/source material, but a standalone EXE does not establish the installed NSIS layout required for in-app updates.

Mac retains explicit enrollment, ad-hoc OS signing and bundled resources. It produces an initial ZIP and `Mogledge.app.tar.gz`, checks codesign, architecture, identifier/version and unchanged executable/material hashes after archive restoration. Developer ID authentication and notarization remain absent.

Each platform's four-file Actions artifact contains its initial ZIP, unsigned updater payload, manifest and checksums. The manifest binds version, full binary source SHA, identifier, target, public configuration hash, executable/source hashes and material/privacy inspection. Candidate archives contain the exact committed source and collected dependency legal texts. Never include PDB/dSYM files, private instructions/configuration, caches, logs, keys or passwords. These are public-repository Actions artifacts, not private storage.

## Signing approval and manual publication

`scripts/release/policy.json` enables signing only after reviewed 0.8.2 build run/artifact identities, exact hashes, expiry and the common binary source are committed. Publication is enabled only after its separate verified-output pins are reviewed and committed. An input cannot enable either operation. Missing, expired, changed or incomplete pins stop processing. The existing public key ID `834723B673FE6C1E` and overlay/feed policy are preserved.

1. **Signing workflow:** `.github/workflows/release-signing.yml` is manual-only. Read-only preparation validates the reviewed main tooling SHA, existing release Environment protection and all three pinned candidates without application execution. The Secrets-using job runs without a deployment reviewer checkpoint under the owner-authorized protected-main policy. It rechecks the exact Environment/main ruleset, provisions the integrity-pinned official signer, receives keys/password only as step environment variables, suppresses diagnostics and disables core dumps. A separate Secrets-free job verifies every signature and the pinned release version using the standalone public-key verifier. It produces the exact archives, signatures, checksums, verification receipt and staged `latest.json`; it cannot publish.
2. **Publication workflow:** `.github/workflows/release-publication.yml` remains a separate manual run; it does not reference an Environment or request a second deployment approval. It remains disabled until a reviewed policy update pins the successful production signing run and its verified output artifact/hash/expiry. Read-only preparation independently rechecks provenance, every asset checksum, all signatures, version and exact feed entries. The selected full main tooling SHA must match the workflow's actual SHA. Only the `publish` job has `contents: write` plus `actions: read`; no signing Secrets are exposed. It repeats validation and the signing Environment protection checks before writes, rejects existing releases/tags, stages and checks every asset in a draft, and publishes only after all uploads match their expected hashes. It does not overwrite assets, force tags or delete a failed draft. Partial failure stops for separate review.

Write permission is limited to the publication job; repository permissions and Secrets values are unchanged. For 0.9.0, the owner explicitly authorized removing Required reviewers from the existing `release` Environment. Production tooling now checks that same Environment ID, an exact main-only deployment policy, disabled administrator bypass, and the active pinned main ruleset requiring PRs and prohibiting force-push/deletion with no bypass actors. The manual workflow triggers, repository/SHA/candidate checks and step-scoped Environment Secrets remain unchanged. The historical signing trial keeps its required-reviewer check and fails closed after this change. No deployment is approved on the owner's behalf. Merging candidate pins enables signing policy only; dispatch and publication remain separate operations. The historical 0.8.2 evidence below records its original two-approval procedure; production signing from 0.9.0 uses the protected-main policy without a deployment reviewer checkpoint.

GitHub's [release creation permission rules](https://docs.github.com/en/rest/releases/releases#create-a-release) require an additional workflow-write permission if a newly tagged binary source has different workflow files from the default branch. This implementation compares those workflow file hashes before publication and stops on a difference; it never adds broader credentials. Complete workflow changes before selecting the binary source, and keep later activation commits limited to reviewed pins/documentation. Release/tag/asset API mutations are separate operations: final asset identity, size, digest and draft/tag source are rechecked immediately before publishing and the actual tag is read back afterward. Protection and assets must remain in force throughout approval and publication; those readbacks are not a transactional lock against concurrent administrator changes.

The publication-approval change does not activate a new release or rewrite the retained 0.8.2 artifact pins. If it merges after a candidate build, those earlier binaries cannot pass the workflow-compatibility check against the changed main. Select a final source containing all intended workflow changes before building an eventual publishable release. An earlier build-only candidate remains build evidence; it is not automatically eligible for signing or publication.
