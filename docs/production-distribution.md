# Mogledge 0.8.2 production distribution preparation

This prepares Windows x64 NSIS, Intel Mac and Apple Silicon Mac distribution from one reviewed source. The product stays 0.8.2, the identifier remains `com.shimilynx.myknowledge`, and the existing NSIS installation identity/template is retained. Installed Windows and Mac 0.8.1 are preserved for the owner's signed in-app update check after publication. No Mac device access, installer execution, Release publication or approval delegation is included in preparation.

The successful [Intel Mac 0.8.1 signing trial](https://github.com/shimi-lynx/mogledge/actions/runs/38568306072) establishes that earlier candidate only. Its policy and workflow remain unchanged. It is not evidence that 0.8.2 has been built or verified.

## Build once from the final candidate source

Merge the reviewed packaging preparation before selecting the final full main SHA. Build all intended 0.8.2 candidates from that same SHA; later policy-only tooling commits have separate SHAs and do not require rebuilding these binaries. Avoid duplicate Actions runs and reuse an existing matching Windows cache with one Rust job; do not copy or clean the cache. Existing installed applications and profiles are not build fixtures.

The manual candidate workflow accepts `updater_app: true` with Windows x64, either Mac target, or all three sequentially. Cost and legal-material confirmations remain required. Standard public-repository runners are used; do not change the existing $0 additional budget, payment method, repository security settings or authentication. Failed operations stop for diagnosis; no blind retry or automatic re-signing is authorized.

Windows compiles the explicit updater overlay once using the native x64 MSVC cache layout. It then bundles that executable as NSIS with CLI updater signing disabled. Neither step receives production Secrets. The existing NSIS template, current-user installation location and uninstaller identity are retained. Inspection checks installer name/PE versions/unsigned status, extracts with existing 7-Zip without executing the installer, and compares the actual bundled EXE and every embedded legal/source file. The bundler's NSIS marker is included in the final payload hash; an earlier unbundled EXE hash is not substituted. The ordinary ZIP also carries the EXE and legal/source material, but a standalone EXE does not establish the installed NSIS layout required for in-app updates.

Mac retains explicit enrollment, ad-hoc OS signing and bundled resources. It produces an initial ZIP and `Mogledge.app.tar.gz`, checks codesign, architecture, identifier/version and unchanged executable/material hashes after archive restoration. Developer ID authentication and notarization remain absent.

Each platform's four-file Actions artifact contains its initial ZIP, unsigned updater payload, manifest and checksums. The manifest binds version, full binary source SHA, identifier, target, public configuration hash, executable/source hashes and material/privacy inspection. Candidate archives contain the exact committed source and collected dependency legal texts. Never include PDB/dSYM files, private instructions/configuration, caches, logs, keys or passwords. These are public-repository Actions artifacts, not private storage.

## Two separate native approvals

`scripts/release/policy.json` initially disables production signing and publication and contains no candidate or verification artifact pins. An input cannot enable either operation. Missing, expired, changed or incomplete pins stop processing. Review and commit actual 0.8.2 build run/artifact identities, exact hashes, expiry and the common binary source before activating signing. Preserve the existing public key ID `834723B673FE6C1E` and overlay/feed policy.

1. **Signing workflow:** `.github/workflows/release-signing.yml` is manual-only. Read-only preparation validates the reviewed main tooling SHA, existing release Environment protection and all three pinned candidates without application execution. The only Secrets-using job waits for the owner's GitHub Environment approval. It rechecks protection, provisions the integrity-pinned official signer, receives keys/password only as step environment variables, suppresses diagnostics and disables core dumps. A separate Secrets-free job verifies every signature and signed 0.8.2 version using the standalone public-key verifier. It produces the exact archives, signatures, checksums, verification receipt and staged `latest.json`; it cannot publish.
2. **Publication workflow:** `.github/workflows/release-publication.yml` is a separate manual run, so it has a fresh native Environment approval rather than reusing signing approval. It remains disabled until a reviewed policy update pins the successful production signing run and its verified output artifact/hash/expiry. Read-only preparation independently rechecks provenance, every asset checksum, all signatures, version and exact feed entries. The owner sees that concrete asset set before approving publication inside GitHub. Only the `publish` job has `contents: write` plus `actions: read`; no signing Secrets are exposed. After approval it repeats validation, rejects existing releases/tags, stages and checks every asset in a draft, and publishes only after all uploads match their expected hashes. It does not overwrite assets, force tags or delete a failed draft. Partial failure stops for separate review.

The permission proposed here is limited to the future publication job; repository permissions, Environment protection and Secrets values are unchanged. Merging this preparation does not enable its committed policy, dispatch a workflow or approve publication. AI must never approve either native deployment on the owner's behalf, even though the connected dispatcher identity belongs to that same owner.

GitHub's [release creation permission rules](https://docs.github.com/en/rest/releases/releases#create-a-release) require an additional workflow-write permission if a newly tagged binary source has different workflow files from the default branch. This implementation compares those workflow file hashes before publication and stops on a difference; it never adds broader credentials. Complete workflow changes before selecting the binary source, and keep later activation commits limited to reviewed pins/documentation. Release/tag/asset API mutations are separate operations: final asset identity, size, digest and draft/tag source are rechecked immediately before publishing and the actual tag is read back afterward. Protection and assets must remain in force throughout approval and publication; those readbacks are not a transactional lock against concurrent administrator changes.

## Exact publication scope

The proposed destination is the public `shimi-lynx/mogledge` GitHub Release **`v0.8.2`**, whose tag must reference the actual common binary source SHA. Publish the Windows unsigned NSIS `*-setup.exe`, Mac ad-hoc `.app.tar.gz` payloads, each generated `.sig`, three initial ZIPs, `verification.json`, `SHA256SUMS.txt` and `latest.json`. Every installer/app includes collected license/source material. Actual asset names and SHA-256 values must be read back from the reviewed candidate/verification records before publication approval.

The embedded anonymous feed stays `https://github.com/shimi-lynx/mogledge/releases/latest/download/latest.json`. Its entries are exactly `windows-x86_64`, `darwin-x86_64` and `darwin-aarch64`, with HTTPS URLs under `releases/download/v0.8.2/` and the contents of each matching `.sig`. Signed and announced versions must both be 0.8.2. No account token is embedded in the app/feed. Updater signatures do not provide Windows Authenticode or Mac notarization; OS trust prompts can remain.

After publishing, the workflow reads that latest-feed URL and each updater payload anonymously and compares them with the reviewed bytes. A failed post-publication check reports failure after publication; it does not retry, delete or silently change already public assets. Read back the actual Release/feed state before any recovery action.

The owner performs actual Mac checks. Signed in-app update, data preservation and restart on the existing Windows/Mac 0.8.1 installations remain follow-up after publication, as agreed. Static fixtures, earlier Native probes and successful packaging do not count as those checks. Existing QA follow-up remains in issues [#9](https://github.com/shimi-lynx/mogledge/issues/9) and [#10](https://github.com/shimi-lynx/mogledge/issues/10); candidate/distribution work remains in [#5](https://github.com/shimi-lynx/mogledge/issues/5).

Production fixtures use opaque payloads, public markers and mocked verification/write APIs; they never generate a key, sign a payload, publish or launch an application. Actual 0.8.2 Windows packaging/resources and Mac builds remain unrun until the final candidate source is merged.
